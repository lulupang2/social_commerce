# 입점사와 거래 설계

상태: 설계 초안, 구현 전 · 기준일: 2026-09-18

첫 거래·테스트 결제 구현의 작업 순서와 검증 조건은
[거래·PG 작업 계획](commerce-payment-work-plan.md)에 정리한다. 문서 작성은 구현 완료가 아니다.

개인 중고거래를 유지하면서 입점사가 상품을 판매할 수 있도록 확장합니다. Go + Fiber가 권한·가격·재고·주문·결제·정산 규칙을 담당합니다. 입점사 추가는 확정 방향이며 아래 거래 정책은 초기 구현을 위한 기본안입니다.

## 초기 범위

- 개인 판매자와 사업자 입점사를 같은 판매 주체 모델로 관리합니다.
- 입점 신청 → 운영자 심사 → 승인 후 판매를 기본 흐름으로 둡니다.
- 한 주문에는 한 판매자의 상품만 포함합니다. 여러 업체를 묶는 결제는 후속 범위입니다.
- 국내 KRW 거래를 초기 결제 범위로 제안합니다. 수수료·배송비·구매확정·반품·정산 주기는 운영 정책으로 확정해야 합니다.
- 주문·정산 기록은 회원 탈퇴나 상품 삭제로 연쇄 삭제하지 않습니다. 보존·익명화 정책은 별도로 확정합니다.

## 회원과 판매 주체

| 예정 모델                                   | 책임·주요 제약                                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------------------ |
| `members`                                   | 로그인하는 사람, [인증 설계](authentication.md)에서 정의                             |
| `sellers`                                   | 판매 주체, `individual` 또는 `business`, 승인·정지 상태                              |
| `seller_memberships`                        | 판매 주체와 회원 관계, `(seller_id, member_id)` 유일, 역할·활성 상태                 |
| `seller_applications`                       | 입점 신청 내용과 심사·반려·승인 이력                                                 |
| `seller_payout_profiles`                    | 지급대행 셀러 식별자·검증 상태, 민감정보 접근 제한                                   |
| `listings` 확장                             | 판매 주체 참조 추가; 현재 `seller_id`는 개인 프로필 FK이므로 바로 의미를 바꾸지 않음 |
| `inventory_items`, `inventory_reservations` | 판매 가능 수량, 주문별 예약 수량·만료·소비 상태                                      |

상품은 `seller_account_id` 같은 새 FK로 판매 주체를 연결하는 기본안을 둡니다. 기존 판매자마다 개인 판매 주체와 소유자 구성원 관계를 생성해 연결하고, 검증 뒤 기존 개인 참조 의존성을 정리합니다. 컬럼 최종 이름은 SQL 설계에서 고정합니다.

## 권한

| 역할 기본안   | 범위                                                                       |
| ------------- | -------------------------------------------------------------------------- |
| 구매자        | 자신의 주문·결제·환불 요청                                                 |
| 업체 대표     | 소속 업체 설정·직원·상품·주문·정산 조회; 정산 계좌 변경은 별도 재인증·검증 |
| 상품 담당자   | 소속 업체 상품·재고 관리                                                   |
| 주문 담당자   | 소속 업체 주문·배송 처리                                                   |
| 정산 담당자   | 소속 업체 정산 조회                                                        |
| 플랫폼 운영자 | 명시적으로 부여된 심사·중재·환불·지급 권한과 감사 기록                     |

모든 업체 자원 요청은 활성 구성원 관계와 대상 자원의 실제 소유 업체를 함께 확인합니다. 요청의 `seller_id`나 UI 메뉴 숨김을 권한 근거로 삼지 않습니다. 업체 정지 시 신규 판매와 기존 주문 처리 권한을 구분합니다.

## 주문과 결제

| 예정 모델               | 보관할 내용                                                            |
| ----------------------- | ---------------------------------------------------------------------- |
| `orders`, `order_items` | 구매자·판매 주체, 주문 당시 상품명·단가·수량·수수료 규칙·배송비 스냅샷 |
| `payment_attempts`      | 주문별 여러 결제 시도, PG 식별자, 승인 금액·통화·상태·멱등 키          |
| `refunds`               | 부분·전체 환불 금액, 사유, PG 취소 결과와 상태                         |
| `shipments`             | 배송 업체·송장·발송·완료 상태                                          |
| `payment_events`        | 웹훅 식별자 유일, 수신·검증·처리·재시도 상태                           |
| `outbox_events`         | DB 변경과 함께 기록한 후속 작업, 재시도·중복 처리 제어                 |

서버가 DB 가격·판매 상태·배송 정책으로 총액을 계산합니다. 초기 KRW 금액은 정수 원 단위로 처리하고, 기존 numeric 가격을 이관할 때 소수·통화·범위를 검증합니다. 금액 계산에 부동소수점을 사용하지 않습니다.

주문·결제·배송·환불·정산 상태는 각각 관리합니다. 상태 전이는 허용된 이전 상태와 행위자를 검사하고 원자적으로 반영합니다.

1. 트랜잭션에서 상품 상태·수량을 확인하고 재고를 예약한 뒤 미결제 주문을 생성합니다. 개인 중고 상품의 기본 수량은 1입니다.
2. PG 인증 결과를 받은 서버가 주문 소유권·통화·금액·기존 승인 여부를 확인하고 승인 요청을 수행합니다.
3. PG 호출 중 DB 트랜잭션을 장시간 유지하지 않습니다. 시도 상태와 멱등 키를 먼저 저장하고 외부 결과를 후속 트랜잭션으로 반영합니다.
4. 승인 실패·시간 초과·응답 유실은 PG 조회로 대조합니다. 승인 여부가 불명확하면 재고를 즉시 해제하거나 무조건 다시 승인하지 않습니다.
5. 예약 만료와 승인 처리가 경쟁해도 초과 판매되지 않도록 잠금·조건부 갱신을 사용합니다. 이미 해제된 재고에 늦게 승인이 확인되면 자동 판매 완료 대신 보상 취소 또는 운영 조정 흐름으로 처리합니다.
6. 결제 결과를 반영하고 배송·구매확정으로 진행합니다. 환불은 승인된 취소 범위와 PG 결과를 확인한 뒤 기록합니다.

웹훅은 PG별 검증 방식으로 출처와 내용을 확인하고 필요한 경우 PG API로 재조회합니다. 이벤트는 영속 저장 후 응답하고 중복·순서 역전·재시도에도 상태가 되돌아가지 않게 처리합니다.

큐는 [River](background-jobs.md)로 확정했습니다. 같은 Supabase DB에서 업무 변경과 작업 등록을 한 트랜잭션에 포함합니다. 외부 전달·별도 감사 목적이 없는 outbox는 중복 생성하지 않습니다.

## 정산과 지급

정산 대상 확정과 실제 지급을 구분합니다. 판매 대금·수수료·환불·조정 내역을 불변 원장에 기록하고 수정은 반대 분개와 새 기록으로 남깁니다. 거래별 금액 합계가 맞는지 검증합니다.

| 예정 모델                               | 역할                                                          |
| --------------------------------------- | ------------------------------------------------------------- |
| `ledger_transactions`, `ledger_entries` | 판매·수수료·환불·조정의 근거, 차변·대변 균형 검증             |
| `settlements`, `settlement_items`       | 업체·기간별 확정 정산과 원장 연결, 같은 항목의 중복 정산 방지 |
| `payout_attempts`                       | 지급 요청·결과·실패·재시도, PG 요청 식별자 유일               |

worker가 정산 대상 계산, 예약 만료, PG 대조와 지급 재시도를 처리합니다. 다중 worker는 작업 소유권과 재시도 시점을 관리하며 외부 지급의 중복 실행을 막습니다. 지급 완료 후 환불은 원장 조정과 다음 지급 차감·회수 정책으로 처리하고, 이미 지급된 금액이 자동 회수된다고 가정하지 않습니다.

테스트 PG는 토스페이먼츠로 확정했습니다. 실제 결제 계약과 판매자 지급대행은 이번 연습 범위에 포함하지 않으며 지급대행 제공자는 아직 미선정입니다. 개인 판매자·사업자 입점사 모두의 지원 여부, 셀러 심사·계좌 검증, 에스크로 필요 여부, 정산 주기를 계약 단계에서 확인합니다. 현재 문서는 법적·계약상 가능 여부나 PG 계약 완료를 의미하지 않습니다.

## 예정 API 영역

`/api/v1/sellers`, `/seller-applications`, `/listings`, `/orders`, `/payments`, `/refunds`, `/settlements`로 영역을 구분하는 기본안입니다. 구체적인 메서드·본문·오류는 각 구현 단계에서 OpenAPI로 확정합니다.

주문 생성·결제 승인·환불·지급에는 작업 범위와 요청 본문에 연결한 멱등 키를 적용합니다. 같은 키로 다른 본문을 보내면 충돌로 거부합니다. 결제·정산·인증 실패를 로컬 데모 성공으로 대체하지 않습니다.

## 첫 완료 목표

승인된 입점사가 상품을 등록하고, 구매자가 테스트 PG로 결제한 주문을 해당 업체만 조회합니다. 타 업체 접근 차단, 마지막 재고 동시 구매, 중복 승인·웹훅, 승인 후 DB 실패·복구를 통과해야 완료로 표시합니다.

실제 지급은 원장 대조·환불·지급 실패 재시도와 운영 정책이 준비된 뒤 별도 단계로 활성화합니다.

## 격리 검토·판매 재고 fixture

`APP_ENV=test`인 격리 fixture에서만 검토자를 등록한다. migration `0017_listing_reviews.sql`은 감사 기록·RLS·DB 권한을 만들지만 운영 권한을 자동 배포하지 않는다. 격리 Compose DB에 migration을 적용한 뒤 `bash ops/nhn-rocky/provision-review-fixture.sh summergear-listings-test`로 검토자 회원과 승인된 판매자 A/활성 소속을 준비한다. 판매자 A가 만든 매물을 검토자가 `/reviews`에서 승인하거나 사유를 남겨 반려한다. 반려 매물은 소유자만 수정·재검토 요청할 수 있다. 상태·검토자·시각·반려 사유는 `listing_review_events`에 남는다. 활성 매물의 일반 수정·이미지 변경은 허용하지 않는다.

승인은 재고를 만들지 않는다. 소유자 A의 승인된 매물 UUID를 지정해 `bash ops/nhn-rocky/provision-review-fixture.sh summergear-listings-test APPROVED_LISTING_UUID`를 *별도로* 실행하면 그 매물의 재고 1개만 준비한다. 스크립트는 정확한 격리 DB명과 marker를 검사하며, 다시 실행해도 동일한 회원·판매자·재고를 중복 생성하지 않고 기존 행을 삭제하거나 운영 DB를 초기화하지 않는다. 다른 구매자 계정에서만 주문을 생성한다. 판매자 승인·재고 연결 없이 공개만 된 매물은 상세에 “판매 준비 중”을 표시한다. 다른 판매자가 이미 연결한 재고는 덮어쓰지 않는다.

## 구매자 주문 화면 (현재 테스트 범위)

`/orders`는 Go API가 반환한 구매자 주문 최근 최대 50건을 최신순으로 보여준다. 결제 승인과 판매자 접수·전달·구매자 수령은 별도 상태로 표시하며, 주문 계약에는 이미지 URL이 없으므로 상품 이미지 대신 이미지 없음 표시를 사용한다. 주문이 없거나 세션·API 요청에 실패하면 각각 빈 목록 또는 오류 안내와 다음 동작을 제공한다.

목록 카드의 긴 상품명은 두 줄까지만 표시하고 전달 안내는 한 줄로 줄인다. 상품명 전체와 자세한 전달 상태 설명은 주문 상세에서 확인할 수 있다.

`/order/[id]`는 주문 당시 상품·금액·결제·전달 상태를 확인하는 화면이다. 구매자는 미결제 주문에서 결제를 계속하거나 주문을 취소할 수 있고, 판매자가 전달을 완료한 주문에서만 수령을 확인할 수 있다. 결제 결과 확인 중 또는 전체 취소 확인 중에는 결제 상태 화면으로 이동해 결과를 확인한다. 이 화면은 테스트 결제만 지원하며 실제 과금·배송이 진행됐다는 뜻은 아니다.

목록의 `수령 확인하기` 링크는 상세의 `#order-actions`로 이동한다. 주문 조회가 성공하고 작업 영역이 렌더링된 뒤 한 번만 스크롤과 키보드 포커스를 옮긴다. 일반 상세 진입이나 조회 실패·접근 권한 없음 상태에서는 자동 이동하지 않는다.
