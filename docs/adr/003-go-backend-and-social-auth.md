# ADR 003: Go 백엔드와 자체 소셜 인증

- 상태: 채택, 구현 전
- 결정일: 2026-09-18
- 범위: 백엔드 분리, 네이버·카카오 로그인, 입점사 확장
- 대체 범위: [ADR 001](001-stack.md)의 백엔드 책임, [ADR 002](002-mobile-mvp-safety-boundaries.md)의 인증·사용자 식별 기준

> 후속 결정: DB는 최종 [ADR 005](005-supabase-river-toss-test.md)에 따라 Supabase 유지, 작업 큐는 River, PG는 토스페이먼츠 테스트 연동으로 확정했습니다. Go 자체 인증 방향은 유지합니다.

## 배경

SummerGear를 개인 중고거래에서 입점사 판매까지 확장합니다. 주문·결제·환불·정산을 담당할 Go + Fiber 백엔드를 추가하고, 네이버와 카카오 로그인을 Go에서 일관되게 처리하기로 결정했습니다.

현재 코드는 Supabase 이메일 OTP, `auth.users`, `auth.uid()`와 브라우저의 Supabase 직접 호출을 사용합니다. 이 문서는 목표 구조에 대한 결정이며 현재 동작이 이미 변경되었다는 뜻은 아닙니다.

## 결정

1. Go + Fiber가 서비스 API, 인증, 접근 권한과 거래 규칙을 소유합니다.
2. 네이버·카카오 인증 요청, 콜백, 회원 연결과 서비스 세션을 Go에서 처리합니다. 목표 구조에서 Supabase Auth를 사용하지 않습니다.
3. 서비스 회원 ID를 외부 로그인 제공자의 ID와 분리합니다. 입점사는 회원과 별도의 판매 주체이며 구성원 관계로 연결합니다.
4. Next.js와 Expo WebView는 유지합니다. Next.js는 화면·SSR·필요한 프록시만 담당하고 거래 규칙을 중복 구현하지 않습니다.
5. 초기에는 하나의 Go 코드베이스를 인증·판매자·상품·주문·결제·정산 모듈로 나눕니다. 장시간 작업은 같은 코드베이스의 worker로 실행합니다.
6. PostgreSQL은 초기에는 Supabase 호스팅을 유지하는 설계 기준을 둡니다. Go 전환이 DB 호스팅 이전을 의미하지는 않습니다. Storage·Realtime의 잔여 의존성은 인증 종료 전에 해결합니다.

## 검토한 대안

| 대안                                     | 판단                                                                |
| ---------------------------------------- | ------------------------------------------------------------------- |
| Supabase Auth 유지                       | 인증 운영 부담을 줄일 수 있지만 이번에 선택한 인증 소유 방식과 다름 |
| 카카오는 Supabase, 네이버는 Go           | 회원 연결과 세션 경로가 둘로 나뉘므로 채택하지 않음                 |
| Go가 두 제공자와 서비스 세션을 모두 관리 | 채택. 로그인과 서비스 권한의 책임을 한곳에 둠                       |

이 결정은 네이버 연동이 Supabase에서 불가능하다는 판단에 근거하지 않습니다. 인증을 Go에 통합한다는 제품·아키텍처 선택입니다.

## 결과와 부담

Go에서 세션 만료·회전·폐기, 계정 연결·탈퇴, 로그인 시도 제한, 비밀키 관리와 감사 기록을 구현하고 운영해야 합니다. 제공자 SDK나 Fiber의 인증 미들웨어만으로 이 책임이 모두 해결되지는 않습니다.

기존 회원의 인증 주체와 FK, RLS, Storage, Realtime 의존성을 이전해야 합니다. 새 세션을 기존 `auth.uid()` 기반 정책이 자동 인식한다고 가정하지 않습니다. 적용 순서와 전환 조건은 [백엔드 전환 설계](../backend-transition.md)에 따릅니다.
