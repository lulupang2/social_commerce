# 거래·토스페이먼츠 테스트 연동 작업 계획

작성일: 2026-09-22. 상태: 초기 작업안과 인수 조건. 키 없는 후속 구현 결과는
[2026-09-22 구현·검증 기록](commerce-payment-verification-20260922.md)을 확인한다.
이번 문서는 구현 범위와 인수 조건을 정리한다. 결제 기능 구현·검증·배포 완료를 의미하지 않는다.
다음 작업용 [구현 프롬프트](prompts/commerce-payment-implementation.md)를 함께 사용한다.

기준은 [거래 설계](commerce.md), [ADR 005](adr/005-supabase-river-toss-test.md),
[테스트 결제 준비](payment-test-setup.md), [인증 설계](authentication.md)다.
이 문서의 초기 범위는 전체 거래 로드맵의 첫 단계이며 입점사·배송·정산을 대체하지 않는다.

실행 직전에 재검증한다. 원격 기존 저장소에는 미커밋 변경이 있으므로 덮어쓰지 않는다.
홈의 데모 카드나 브라우저 로컬 매물을 결제 가능한 서버 상품으로 취급하지 않는다.

## 첫 구현 범위

- 승인된 테스트 판매자 1곳, 서버에 저장된 판매 가능 상품, 주문당 상품 1종·수량 1개.
- KRW 정수 금액, 토스페이먼츠 테스트 카드 결제, 승인·조회·전체 취소.
- 주문 생성 시 가격 스냅샷과 재고 예약, 구매자 본인 주문 조회, 해당 판매자 주문 조회.
- 중복 주문·승인·취소 방지, 응답 유실·재시작·예약 만료 복구.
- 웹 우선 검증. 모바일 결제창·외부 앱 복귀는 별도 검증 항목으로 기록한다.

장바구니, 여러 판매자 묶음 주문, 쿠폰·포인트, 부분 취소, 가상계좌·정기결제,
배송사 API, 판매자 실지급, 실제 과금은 첫 범위에 포함하지 않는다.
판매자 승인·구성원 권한의 최소 모델은 포함하되 입점 신청·심사 관리 UI는 후속으로 둔다.

## 테스트 정책과 미확정 사항

다음 값은 구현을 진행하기 위한 테스트 기본안이다. 운영 정책으로 확정된 값이 아니다.

| 항목 | 테스트 기본안 / 결정 시점 |
| --- | --- |
| 배송·수수료 | 배송 없는 테스트 상품, 배송비·수수료 0원. 서버 주문 스냅샷에 명시 |
| 재고 | 상품당 1개. 매물 상태와 별도의 예약 모델을 사용하고 기존 상태 의미는 보존 |
| 예약 시간 | 15분 기본안. 실제 PG 승인 가능 시간과 공식 가이드를 대조해 구현 시 확정 |
| 자기 상품 구매 | 거부 |
| 환불 | 이행 전 전액 취소만. 구매자 본인·권한 있는 판매자/운영자의 허용 범위를 계약에 명시 |
| 실제 운영 | 수수료·배송·반품·구매확정·정산 주기·PG 계약 범위는 별도 결정 |

공용 임시 로그인으로 구매자별 주문 보호를 검증할 수 없다.
키 없는 테스트에서는 기존 인증 fixture를 활용해 구매자 A/B·판매자 A/B 세션을 분리한다.
실제 PG 테스트 화면을 외부에 제공하기 전에는 독립 회원 세션과 접근 범위를 갖춰야 한다.
임의 회원 ID 입력으로 로그인되는 공개 엔드포인트를 추가하지 않는다.
소셜 제공자 전체 구현은 별도 작업이지만, 공용 계정을 실제 구매자 인증의 대체재로 삼지 않는다.

## 구현 순서와 산출물

### 1. 현재 계약 확인과 거래 기반

- 실제 migration·쿼리에서 `public.listings`와 `summergear_app.listings`의 소유권을 비교한다.
  기존 거래 설계의 판매자 컬럼 설명을 현재 Go 모델에 그대로 적용하지 않는다.
- 판매 주체·활성 구성원·승인 상태를 최소 모델로 구현한다.
- 주문·주문 항목·재고 예약·결제 시도·취소·PG 이벤트를 새 migration으로 추가한다.
- 회원 탈퇴·상품 삭제가 거래 기록을 연쇄 삭제하지 않도록 FK와 보존 정책을 명시한다.
- 새 migration 번호는 현재 목록에서 확인한다. 적용된 파일을 편집하거나 번호를 재사용하지 않는다.

완료 조건: 서로 다른 구매자·판매자의 조회/변경 차단, 마지막 재고 동시 구매 시 한 주문만 예약,
예약 취소·만료 후 재고 복원, 기존 매물 등록·조회·수정 회귀 통과.

### 2. 주문과 결제 계약

아래는 제안 경로이며 아직 제공되는 API가 아니다. 구현 시 OpenAPI·Go·웹 Zod·테스트를 함께 확정한다.

| 제안 API | 책임 |
| --- | --- |
| `POST /api/v1/orders` | 매물 ID·수량을 받아 서버 가격으로 주문·예약 생성 |
| `GET /api/v1/orders` | 세션 회원의 주문 목록 |
| `GET /api/v1/orders/{id}` | 구매자 또는 허용된 판매자 권한으로 주문 조회 |
| `POST /api/v1/orders/{id}/cancel` | 미결제 주문 취소. 승인 중·결과 불명은 먼저 PG 대조 |
| `POST /api/v1/orders/{id}/payments/confirm` | 주문 소유권·금액·통화 검증 후 테스트 승인 |
| `POST /api/v1/orders/{id}/refunds` | 권한·잔여 취소 가능액 검증 후 전액 취소 |
| `POST /api/v1/payments/toss/webhook` | 제공자 이벤트 수신·검증·영속 저장·비동기 대조 |

회원 ID·판매자 ID·상품 가격·할인·총액을 브라우저 값만으로 신뢰하지 않는다.
결제 결과의 `orderId`, `paymentKey`, `amount`는 서버 주문·결제 시도와 대조한다.
주문 생성·승인·취소의 멱등 키는 사용자·작업·본문에 묶고 동일 키의 다른 본문은 409로 거부한다.
401/403/404, 재고·상태 충돌 409, 입력 오류, PG 장애와 결과 불명을 각각 계약에 정의한다.
웹훅은 브라우저 CSRF 흐름과 구분하고 해당 이벤트의 공식 검증 방식 및 PG 조회 결과로 검증한다.

완료 조건: 키 없이 가짜 PG로 성공·거부·지연·응답 유실을 검증하고, 실패를 성공 응답이나
로컬 주문으로 바꾸지 않는다. 성공 리다이렉트 도착만으로 결제 완료 표시하지 않는다.

### 3. 상태 전이·재고와 River 복구

상태명은 초안이며 migration/OpenAPI에서 확정한다. 주문·결제·예약·환불 상태는 분리한다.

| 상황 | 처리 원칙 |
| --- | --- |
| 주문 생성 | 가격·판매 상태 확인, 예약과 주문을 한 트랜잭션에서 저장 |
| 승인 요청 | 결제 시도를 먼저 저장하고 트랜잭션 종료 후 PG 호출 |
| 승인 성공 | 검증한 결과로 결제·주문·예약 소비를 원자적으로 반영 |
| 승인 timeout·응답 유실 | 결과 불명으로 기록, 재승인·재고 해제 대신 PG 조회 |
| PG 성공 후 DB 실패 | River 대조로 승인 복원; 재고 이미 해제됐다면 보상 취소/운영 확인 |
| 예약 만료와 승인 경쟁 | 잠금·조건부 갱신으로 처리 순서를 결정, 승인 진행/불명 상태 보존 |
| 취소 timeout | 미확정 취소로 기록하고 PG 조회로 확정; 선제 환불 완료 처리 금지 |
| 중복·역순 웹훅 | 중복 제거 후 PG 현재 상태 대조, 최종 상태를 과거 상태로 되돌리지 않음 |

PG 결제 식별자·주문 관계와 승인/취소 중복은 DB 제약으로도 보호한다.
실패 후 재시도는 새로운 주문이나 PG 효과를 무조건 생성하지 않는다.
업무 변경과 River 등록은 같은 DB 트랜잭션에 넣고, 주기적 대조가 미완료 결제 시도를 다시 찾게 한다.
재시도 한도·간격·최종 운영 확인 상태·관측 지표를 정한다. 별도 outbox는 필요한 근거가 있을 때만 추가한다.
웹훅 검증 규칙·이벤트 종류는 현재 공식 문서를 확인하며 임의의 공통 서명 헤더를 가정하지 않는다.

### 4. 웹 결제 흐름

`실제 상품 상세 → 구매하기 → 주문서 → 토스 결제창 → 서버 승인 확인 → 주문 상세`를 구현한다.
결과 불명은 “결제 결과 확인 중”으로 표시하고 주문 조회로 복구한다.
새로고침·뒤로가기·버튼 연타·실패 URL 접근에도 중복 결제나 거짓 성공을 만들지 않는다.
데모 상품은 구매 대상이 아님을 표시하고 결제 요청 자체를 만들지 않는다.
취소 요청과 취소 완료를 구분하고, 주문 내역을 다시 열어 서버 상태를 확인할 수 있게 한다.

완료 조건: 가짜 PG 브라우저 흐름과 실제 PG 테스트 흐름을 별도로 기록한다.
WebView 외부 결제 앱 실행·복귀·쿠키 연속성을 미검증 상태로 남긴 경우 명확히 보고한다.

### 5. 실제 테스트 키 연결과 테스트 배포

기존 `.env.example`의 `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`, `TOSS_SUCCESS_URL`, `TOSS_FAIL_URL`은
예약된 이름이며 현재 실행 코드에서 소비되는 설정으로 간주하지 않는다.
구현하면서 파싱·설정 검사·역할별 Compose 전달·빈 예시를 함께 추가한다.
`PAYMENT_MODE=test`와 기존 test DB 가드를 유지하고 live 키·혼합 키를 거부한다.
키 미설정 시 프로세스·기능 상태를 명확히 구분하며 테스트 승인 성공으로 위장하지 않는다.
공개 client key 전달 방법은 SDK 선택 후 정하고 secret은 서버 전용 runtime 설정에만 둔다.

공식 SDK 방식과 키 종류는 실제 연동 시 재확인한다:
[키](https://docs.tosspayments.com/reference/using-api/api-keys),
[결제 흐름](https://docs.tosspayments.com/guides/v2/get-started/payment-flow),
[결제창형 연동](https://docs.tosspayments.com/guides/v2/payment-widget/integration-window).

공개 fixture preview에 PG 키를 추가하는 것을 기본 배포 방식으로 삼지 않는다.
Supabase 테스트 환경·분리된 계정·전용 runtime 설정을 준비하고, 배포 직전에 대상·백업·이미지 ID를 기록한다.
API/worker는 migration을 시작 시 실행하지 않고 단일 migration 성공 후 기동한다.
운영 배포·live 결제·실지급은 후속 명시적 요청 범위다.

## 필수 검증 행렬

| 범위 | 최소 시나리오 |
| --- | --- |
| 권한 | 구매자 A/B, 판매자 A/B, 미인증·CSRF·정지 판매자·자기 상품 구매 |
| 금액 | 변조된 가격·주문 ID·다른 주문 paymentKey·통화·0/음수·오버플로 |
| 재고 | 마지막 1개 동시 구매, 예약 만료와 승인 경합, 중복 해제·중복 소비 |
| 멱등성 | 중복 승인/취소, 동일 키 다른 본문, 다른 키로 같은 주문 승인 경쟁 |
| 복구 | PG 성공 후 DB 실패, 승인/취소 timeout, worker 재시작, 웹훅 중복·위조·역순 |
| 브라우저 | 정상·실패·결과 확인 중, 새로고침, 뒤로가기, 중복 클릭, 주문 재조회 |

실행 명령은 저장소 `AGENTS.md`를 따른다. 웹은 루트에서 `pnpm typecheck`,
`pnpm --filter @icegear/web test`, `lint`, `build`를 실행한다.
Go는 Linux `apps/api`에서 `go test ./...`, `go vet ./...`,
`go test -tags=integration ./... -run '^$'`와 실제 격리 DB 통합 테스트를 수행한다.
마지막 명령은 컴파일 검사이며 실제 DB 테스트를 대신하지 않는다.
신규 거래 DB 테스트는 기존 `ops/deployment/check-db.sh` 등 실제 실행 경로에 포함한다.
인증·매물·RLS 변경 시 기존 격리 회귀 검사도 수행한다. 서버에서 빌드와 DB 검사는 순차 실행한다.

## 완료 보고와 제외 범위

- 코드 구현, 키 없는 검증, 실제 토스 테스트 검증, 테스트 배포를 각각 구분해 보고한다.
- 변경 파일·계약·migration·환경변수·호환성·실행 명령·결과·로그 위치를 기록한다.
- 키가 없으면 가능한 구현과 fixture 검증을 완료하고 실제 PG 검증만 미완료로 표시한다.
