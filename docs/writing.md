# 문서 작성 규칙

독자가 다음 행동을 결정할 수 있도록 짧고 구체적으로 씁니다.
문서는 코드와 함께 저장하고, 동작이 바뀌는 변경에 관련 문서도 포함합니다.

## 문서마다 하나의 역할

| 문서                 | 담을 내용                                |
| -------------------- | ---------------------------------------- |
| 루트 README          | 제품 소개, 빠른 시작, 주요 문서 링크     |
| 문서 목차            | 목적별 읽기 경로                         |
| 개발 가이드          | 환경 구성, 실행, 검증 절차               |
| SSOT                 | 제품 범위와 유지해야 할 원칙             |
| 아키텍처             | 구성 요소의 책임과 데이터 흐름           |
| 데이터 모델·API 계약 | 필드, 제약, 요청·응답, 오류와 경계       |
| 로드맵               | 예정·진행·완료 작업과 검증 근거          |
| ADR                  | 결정 당시의 배경, 대안, 선택 이유와 결과 |

같은 설정이나 계약을 여러 문서에 복사하지 않습니다. 요약이 필요하면 짧게 설명하고 상세 문서로 연결합니다.
실행 명령과 버전은 [package.json](../package.json), 환경변수 목록은 각 앱의 `.env.example`, DB 구조는 [마이그레이션](../supabase/migrations)을 함께 확인합니다.
문서와 코드가 다르면 차이를 확인한 뒤 구현 오류인지 문서 누락인지 판단합니다.

## 읽기 쉬운 구성

- 제목 바로 아래에 문서의 목적을 한두 문장으로 씁니다.
- 제목은 `환경 설정`, `판매글 등록`처럼 찾을 대상이나 행동으로 씁니다.
- 절차는 번호 목록, 비교와 필드 명세는 표, 구조와 흐름은 Mermaid를 사용합니다.
- 명령에는 실행 위치와 필요한 전제 조건을 적습니다.
- 장식용 이모지, 반복 구분선, 의미 없는 강조는 줄입니다.
- 상대 링크로 관련 문서와 구현 파일을 연결합니다.

## 상태와 근거

`구현됨`, `검증됨`, `배포됨`을 구분합니다. 하나의 상태가 나머지를 보장하지 않습니다.
검증 결과를 기록할 때는 실행한 명령, 확인 범위, 결과와 날짜를 함께 남깁니다.
문구만 고쳤다면 검토일을 바꾸거나 새로 검증했다고 적지 않습니다.

ADR은 결정의 이력입니다. 기존 결정을 대체할 때는 새 ADR을 추가하고 이전 문서에 연결합니다.

## 변경을 마치기 전에

1. 예제의 명령·경로·필드가 실제 코드와 맞는지 확인합니다.
2. 새 문서를 [문서 목차](README.md)에 연결하고 상대 링크를 확인합니다.
3. 중복 설명을 줄이고 관련 기준 문서를 함께 갱신합니다.
4. 수정한 Markdown 파일에 Prettier 검사를 실행합니다.
