# 테스트 프로젝트 개선 작업 지시서

작성일: 2026-09-27. SummerGear의 테스트 로그인부터 매물 등록·검색·거래·내역 확인까지 연결하기 위한 구현 지시서다. SNS 로그인은 후속 작업이며 이번 범위에 포함하지 않는다.

이 문서는 작업 계획이다. 아래 구현 관찰과 과거 검증 결과가 향후 작업의 완료를 의미하지 않는다. Orca에 전달할 문안은 [실행 프롬프트](prompts/test-project-improvement.md)에 있다.

## 1. 작업 기준과 시작 절차

- 원본 작업 폴더: `C:\work2\temp\socialapp`.
- 작성 시 브랜치: `main`, HEAD: `0cb22f9`. 현재 상태는 실행 전에 다시 확인한다.
- 이미지·주문·결제·preview 관련 수정과 미추적 파일이 다수 존재한다. 이 문서는 해당 작업 트리를 포함해 작성했다. 원격 `main`이나 새 워크트리에 같은 코드가 있다고 가정하지 않는다.
- 기존 미커밋·미추적 변경을 보존하고 임의 reset·stash·덮어쓰기로 작업 상태를 바꾸지 않는다. 이 작업에 필요한 로컬 브랜치 생성·전환과 워크트리 활용은 허용한다. 다른 체크아웃에서는 필요한 미커밋 코드가 누락되지 않았는지 먼저 대조하고, 작은 작업에 불필요한 작업 공간을 만들지 않는다.
- 문서를 읽는 단계에서 멈추지 말고, 사용자가 선택한 단계의 구현·계약 정렬·검증·완료 기록까지 수행한다. 지정하지 않았다면 **1단계**가 기본 범위다.
- 사용량 절감을 위해 기본은 단일 에이전트로 진행한다. 이 문서는 병렬 에이전트 생성이나 역할 분배 지시가 아니다.

시작할 때 저장소 루트에서 실행한다.

```sh
git status --short --branch
git worktree list
git log -5 --oneline
```

## 3. 목표와 제외 범위

목표는 테스트 계정으로 자신의 데이터를 다시 찾고, 판매자와 구매자 역할로 핵심 흐름을 반복 검증하는 것이다. 웹을 우선 구현하고 Expo WebView의 기존 계약을 보존한다.

이번 계획에서 제외하는 기능:

- 네이버·카카오 등 실제 SNS 로그인과 계정 연결.
- 실결제·실지급, 정산, 배송사 연동, 장바구니·쿠폰·포인트·부분 환불.
- 외부 날씨·파도 API 도입, 대규모 추천 인프라, UI 전면 재설계.
- 기존 운영 데이터 삭제·강제 이전, 원격 push와 실제 배포.

외부 키가 없는 경우에도 가능한 코드 구현과 격리 fixture 검증은 완료한다. 실제 Storage·Toss·실기기 검증은 별도 결과로 남긴다.

## 4. 구현 단계

### 1단계: 목록 상태와 기존 화면 연결 정리 — 기본 실행 범위

목표: 서버 오류·데모·실제 테스트 데이터를 구분하고 기존 주문 화면으로 자연스럽게 이동한다.

- 목록의 성공·빈 목록·인증 문제·네트워크/서버 오류를 구분한다. 정상 빈 응답이나 오류를 데모 성공으로 바꾸지 않는다.
- 데모 체험은 유지하되 선택한 모드와 데이터 출처가 분명해야 한다. 데모 항목이 서버 전체 건수나 구매 가능한 상품으로 표시되지 않게 한다.
- `source` 타입과 소비자를 함께 정리한다. Go 데이터를 Supabase로 표시하는 현재 상태를 바로잡는다. 식별자는 출처와 함께 취급하고 기존 ID 중복 처리·상세 진입을 회귀 검증한다.
- 매물 생성·수정 뒤 캐시 무효화/재조회, 재시도와 로딩 표시를 연결한다. 검토 대기 매물을 공개 목록에 임의로 넣지 않는다.
- 마이페이지에 기존 `/orders` 진입점을 추가하고 주문 화면의 뒤로가기·마켓 복귀 경로를 정리한다.
- 결제 제공자와 상태에 맞는 문구를 사용한다. 제공자를 확정할 수 없으면 중립적인 테스트 결제 문구를 쓴다. 결제 결과 확인 중·취소 확인 중을 성공으로 표시하지 않는다.
- 내 판매·찜·내 글의 실제 개인화 조회는 2·5단계 범위로 남긴다. 1단계에서 이 메뉴까지 완성했다고 보고하지 않는다.

완료 조건: 서버 빈 목록·503·재시도·데모 모드가 서로 다른 화면 상태로 확인된다. 수정한 데이터가 서버 조회 가능한 화면에서 갱신되고, 마이페이지→주문 목록→상세→마켓 이동이 가능하다. 기존 이미지 재시도·정렬·서명 URL 복구가 유지된다.

### 2단계: 테스트 계정·프로필·찜·내 판매 내역

목표: SNS 로그인 없이도 동일한 Go 회원으로 개인 기능이 동작한다.

- 기존 테스트 로그인과 세션 만료·로그아웃을 재사용한다. 프로필·찜·내 판매 조회를 Go 회원 컨텍스트로 연결한다.
- 필요한 Go API·DB·Zod 계약과 회원별 권한을 함께 구현한다. Go 회원/매물 ID를 기존 `public` 테이블의 Supabase Auth ID와 같은 것으로 취급하지 않는다.
- 구매자 A/B, 판매자 A/B를 반복 사용할 수 있는 격리 fixture를 준비한다. 기존 독립 구매자 로그인과 충돌하지 않게 한다.
- 계정 선택은 서버에서 허용한 fixture 역할만 사용하고 `AUTH_DEV_LOGIN_ENABLED`와 명시적 테스트 환경 검사를 유지한다. 임의 회원 ID나 운영자 권한을 요청 바디로 받아 로그인시키지 않는다.
- 공용 preview에는 공유 판매자·운영자 계정 전환을 그대로 노출하지 않는다. 반복 역할 선택은 로컬/격리 fixture에서 수행하고 공개 테스트 로그인은 기존 격리 원칙을 유지한다.
- 찜 저장 실패를 성공으로 남기지 않는다. 계정 변경·로그아웃 시 이전 회원의 캐시를 비우고 재조회한다.
- 마이페이지의 실제 내 판매 목록·찜 목록과 프로필 설정을 연결한다. 수치는 실제 조회 기준을 정하고 데이터가 없는 신뢰 점수는 가짜 수치 대신 미집계로 표시한다.
- 기존 Supabase 기능의 소비자를 확인하고 이전한 쓰기 경로의 권한을 정리한다. 운영 계정 삭제나 근거 없는 자동 데이터 병합은 하지 않는다.

완료 조건: 구매자 A의 찜·프로필·판매글이 B에게 섞이지 않는다. 새로고침·재로그인 이후 동일 회원 데이터가 유지되고 계정 전환 뒤 이전 데이터가 남지 않는다. 미인증·타인 접근·CSRF 검사가 통과한다.

### 3단계: 판매 검토와 구매 가능한 테스트 상품 준비

목표: 등록한 매물을 검토하고 실제 주문 테스트 대상으로 만들 수 있다.

- 테스트 운영자에게만 허용되는 검토 목록·승인·반려 경로와 최소 UI를 추가한다. 역할과 상태 전이는 서버에서 검사한다.
- 반려 사유, 판매자 수정·재검토 요청, 공개 목록 노출을 연결한다. 검토자·시각·이전/이후 상태를 감사 기록으로 남긴다.
- 현재 이미지 수정 가능 상태를 유지한다. 활성 매물의 수정을 단순 허용하지 말고 기존 이미지·공개 상태 계약과 일치시키며 필요한 재검토 정책을 기록한다.
- 매물 승인과 결제 가능한 재고 준비는 별개다. 현재 판매 주체·활성 구성원·`inventory_items` 연결을 확인하고 승인된 테스트 판매자의 상품을 준비하는 fixture 절차를 제공한다.
- 일반 매물 승인만으로 판매자 승인/재고를 자동 부여하지 않는다. 구매 불가능한 매물은 이유가 분명한 안내를 표시한다.
- 테스트 fixture는 실행별 소유 범위가 명확하고 재실행 가능해야 한다. 이번 실행이 만든 데이터만 초기화하며 전체 DB 삭제를 초기화 방식으로 쓰지 않는다.

완료 조건: 판매자 등록→이미지 첨부→검토 대기→운영자 승인/반려→판매자 상태 확인→공개 검색 흐름을 두 개 이상의 세션으로 검증한다. 별도로 준비된 테스트 재고에 대해 다른 구매자의 주문 생성이 가능하다. 구매자·일반 판매자는 승인 API를 호출할 수 없다.

### 4단계: 서버 검색·정렬·페이지네이션

- 검색·종목·카테고리 조건을 서버에 전달한다. 가격 범위·지역 조건과 최신순·가격순 정렬을 추가한다.
- 기존 최신 24개 제한을 명시적인 페이지 크기와 다음 페이지 계약으로 확장한다. 안정적인 보조 정렬 키로 중복·누락을 방지한다.
- 필터를 URL에 반영해 뒤로가기·새로고침 시 복원한다. 조건 변경 시 페이지를 초기화하고 이전 요청의 늦은 응답이 최신 결과를 덮지 않게 한다.
- 전체 건수를 계산하지 않는 API라면 받은 개수를 전체 상품 수라고 표시하지 않는다. 검색 입력 길이·가격 범위·정렬 값·페이지 크기는 서버에서 검증한다.

완료 조건: 최소 30개 서버 fixture로 첫 24개 밖의 상품이 검색되는지 확인한다. 연속 페이지·필터 변경·동일 가격·빠른 검색어 변경·빈 결과·실패 후 재시도를 검증한다.

### 5단계: Go 회원으로 문의·채팅·커뮤니티 연결

- Go 세션과 매물 소유권을 기준으로 구매자/판매자 대화방 생성·조회·메시지·읽음 처리를 연결한다. 대화방 중복 생성과 타인 접근을 차단한다.
- 실시간 전송은 기존 환경에 맞는 방식을 결정하고 근거를 기록한다. Supabase Realtime이 Go 쿠키를 자동 인증한다고 가정하지 않는다. 초기에는 인증된 주기 조회도 허용하되 지연 특성과 재연결 동작을 명시한다.
- 실패한 메시지 재전송 시 중복 저장을 방지하고 서버 실패를 데모 대화로 대체하지 않는다. 알림 배지와 채팅 목록도 서버 상태에 맞춘다.
- 커뮤니티 작성·수정·댓글·반응 등 현재 회원 의존 쓰기 경로를 조사하고 Go 회원 경계로 순차 연결한다. 기존 검토·공개·소유권 규칙을 보존한다.
- 마이페이지의 내가 쓴 글을 실제 개인 목록으로 연결한다. 레거시 작성자를 새 테스트 회원으로 임의 매핑하지 않는다.

완료 조건: 구매자와 판매자가 다른 브라우저 세션에서 대화를 주고받고 읽음 상태가 갱신된다. 제3자는 메시지를 읽거나 쓸 수 없다. 내 글·댓글·반응은 재접속 후 유지되고 계정 간 권한이 분리된다.

### 6단계: 맞춤 추천과 전체 흐름 자동 검증

- 프로필에 저장한 종목·실력·예산·지역을 실제 매물 필드와 비교하는 규칙 기반 점수를 적용한다. 필요한 설정 UI와 계약을 함께 구현한다.
- 추천 이유는 실제로 일치한 조건에서 생성한다. 정보가 없으면 임의로 맞춤이라고 표시하지 않고 최신 상품 등 명시적인 기본 정렬을 사용한다.
- 동점 정렬·추천 후보 범위·판매 불가 항목 제외 기준을 정하고 테스트한다. 추천 인프라나 외부 AI 서비스 도입은 범위 밖이다.
- 각 단계에서 확보한 회귀 검증을 묶어 반복 가능한 브라우저 E2E 실행 경로를 제공한다. 도구 추가가 필요하면 기존 패키지 관리 규칙에 맞춰 의존성과 lockfile을 함께 갱신한다.

완료 조건: 사용자 설정 변경 시 추천 결과/순서/이유가 예측 가능하게 바뀐다. 아래 핵심 흐름을 격리된 실제 Go API·DB와 연결해 검증하며 브라우저 응답 모킹 검증과 구분한다.

## 5. 공통 인수 시나리오

각 단계에 해당하는 시나리오는 그 단계에서 검증한다. 전체 E2E 구축을 이유로 앞 단계 검증을 미루지 않는다.

| 시나리오 | 기대 결과 |
| --- | --- |
| 로그인·전환·만료 | 현재 회원이 분명하며 이전 회원의 개인 데이터가 남지 않는다. 재로그인 후 복귀 흐름이 있다. |
| 등록·검토·노출 | 대기/반려는 소유자·검토자만 접근하고 승인된 매물이 공개된다. 이미지 정책이 유지된다. |
| 검색·찜·내역 | 첫 페이지 밖 상품을 찾고 찜한 뒤 재접속해 개인 목록에서 확인한다. |
| 문의·커뮤니티 | 다른 세션과 통신하고 소유자/참여자 외 접근이 차단된다. |
| 주문·취소 | 준비된 서버 재고만 주문하며 서버 금액을 사용한다. 승인·전체 취소 결과를 서버에서 확인한다. |
| 응답 유실·중복 클릭 | 중복 주문/메시지/결제 효과를 만들지 않는다. 확인 중과 실패를 성공으로 꾸미지 않는다. |
| 서비스 장애 | API·Storage 실패를 표시하고 재시도할 수 있다. 데모 성공이나 빈 정상 응답으로 숨기지 않는다. |

PG 검증은 기존 fake 제공자를 통한 격리 테스트와 실제 Toss 테스트 키를 사용한 확인을 분리한다. 실제 카드 인증이나 외부 키가 필요한 단계는 미검증으로 기록하고 나머지 독립 작업은 진행한다.

## 6. 계약·데이터·검증 규칙

- API·핸들러·서비스·OpenAPI·생성 타입·웹 런타임 검증·테스트를 함께 갱신한다. 신규 API 경로와 타입명은 기존 구조를 확인한 뒤 확정한다.
- 기존 migration을 수정하거나 번호를 재사용하지 않는다. 현재 최대 번호를 확인하고 새 migration을 추가한다. 이번 관찰에는 `0015_toss_test.sql`까지 존재하지만 다음 번호를 고정해서 가정하지 않는다.
- 트랜잭션 범위의 회원 컨텍스트, RLS, private Storage, 서버 금액 검증, API/worker/migration 분리를 유지한다.
- 환경변수는 실제 사용 코드를 확인한다. 신규 변수가 필요하면 파싱·검증·빈 예시·관련 배포 계약을 정렬하되 실제 키를 문서에 넣지 않는다.
- 실제 코드 변경 없이 문서 정리만 했다면 구현 완료로 표시하지 않는다. 테스트를 통과시키기 위한 검증 삭제·근거 없는 skip·기능 비활성화는 금지한다.

웹 변경은 저장소 루트에서 실행한다.

```sh
pnpm typecheck
pnpm --filter @icegear/web test
pnpm --filter @icegear/web lint
pnpm --filter @icegear/web build
```

공통 도메인 변경 시 domain build/test, 모바일 계약 변경 시 관련 모바일 검증과 필요에 따라 `pnpm export:mobile:web`을 추가한다. Go 변경은 `gofmt` 후 Linux의 `apps/api`에서 다음을 실행한다.

```sh
go test ./...
go vet ./...
go test -tags=integration ./... -run '^$'
```

인증·매물·이미지·RLS 변경 시 Linux 저장소 루트에서 실행한다. 신규 회원·채팅·커뮤니티 모듈을 추가하면 해당 DB 통합 검사도 실제 실행 경로에 포함한다.

```sh
bash ops/nhn-rocky/test-listings-database.sh
```

integration 빈 실행은 컴파일 검사다. DB 통합 통과로 보고하지 않는다. CI/Docker/Compose 변경 시 [배포 검증 지침](../ops/deployment/README.md)을 따른다. 브라우저 검사, 실기기 검사, 실제 서비스 검사를 각각 구분한다.
