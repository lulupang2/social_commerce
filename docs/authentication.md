# 네이버·카카오 인증 설계

상태: 설계 초안, 구현 전 · 기준일: 2026-09-18

Go가 두 소셜 제공자의 로그인과 SummerGear 세션을 관리합니다. 기술 방향은 [ADR 003](adr/003-go-backend-and-social-auth.md)에서 확정했으며, 아래 API와 세션 기본안은 구현 계약을 구체화하기 위한 설계입니다.

## 책임

| 구성 요소     | 책임                                                               |
| ------------- | ------------------------------------------------------------------ |
| 네이버·카카오 | 제공자 계정 인증, 동의와 사용자 식별 정보 제공                     |
| Go 인증 모듈  | 로그인 트랜잭션, 코드 교환, 사용자 식별, 회원 연결, 세션 발급·폐기 |
| Go 권한 모듈  | 회원 제재, 업체 소속, 역할, 자원 접근 확인                         |
| Next.js·Expo  | 로그인 진입과 복귀, 로그인 상태 표시                               |

Supabase Auth와 이메일 OTP는 목표 인증에서 제외합니다. 소셜 로그인 성공은 입점 승인이나 플랫폼 운영자 권한을 부여하지 않습니다. 이메일·실명·전화번호는 제공자 동의와 설정에 따라 없을 수 있으며, 로그인 성공을 사업자 또는 정산 계좌 검증으로 취급하지 않습니다.

## 브라우저 로그인

1. Go의 로그인 시작 API가 허용된 제공자를 확인하고 일회성 로그인 트랜잭션을 만듭니다.
2. 트랜잭션에는 제공자, 만료, 요청 브라우저에 대한 바인딩, 검증한 복귀 경로, `state`와 필요한 PKCE·OIDC nonce를 저장합니다. 표준 라이브러리로 처리하고 제공자 지원 방식은 어댑터별로 검증합니다.
3. 제공자 인증·동의 후 등록된 Go 콜백으로 돌아옵니다. 거부·오류·만료·재사용을 구분합니다.
4. Go가 `state`와 브라우저 바인딩을 확인한 뒤 코드를 서버에서 교환합니다. OIDC 사용 시 서명·issuer·audience·만료·nonce를 검증합니다. OAuth 사용자 정보 사용 시 서버가 받은 토큰으로 제공자 API를 호출합니다.
5. 검증한 제공자 사용자 ID로 회원을 찾습니다. 신규 회원은 서비스 약관 동의 등 온보딩을 완료하기 전 거래 권한을 제한합니다.
6. Go가 새 서비스 세션을 발급하고 허용된 내부 경로로 복귀시킵니다. 기존 세션 ID를 재사용하지 않습니다.

카카오·네이버의 OAuth/OIDC API 차이는 제공자 어댑터에 한정합니다. 제공자 코드를 브라우저에서 교환하거나 서비스 API의 로그인 토큰으로 제공자 access token을 받지 않습니다.

## 세션 기본안

현재 클라이언트가 웹과 WebView이므로 서버 저장형의 불투명 세션을 기본안으로 둡니다. JWT 발급을 필수로 두지 않습니다.

- 세션 원문은 충분한 난수로 생성하고 운영 환경에서 `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`의 호스트 전용 쿠키로 전달합니다.
- DB에는 세션 토큰의 해시, 회원 ID, 생성·최종 활동·유휴 만료·절대 만료·폐기 시각을 저장합니다. 구체적인 유효기간은 API 기반 단계에서 확정합니다.
- 로그인·권한 상승 시 세션을 회전하고 이전 세션을 폐기합니다. 활동에 따른 만료 연장은 절대 만료를 넘지 않습니다.
- 변경 API는 CSRF 토큰과 Origin 검증을 적용합니다. SameSite 설정만으로 모든 CSRF 방어를 대신하지 않습니다.
- 브라우저는 동일 출처 API를 사용하고 다른 출처 허용은 명시적 목록으로 제한합니다. SSR 요청은 필요한 세션 쿠키만 Go로 전달합니다.
- 로그아웃은 서버 세션 폐기와 쿠키 삭제를 함께 수행합니다. 전체 기기 로그아웃·계정 정지·탈퇴 시 관련 세션을 모두 폐기합니다.
- 세션 조회 실패 시 인증 성공으로 처리하거나 로컬 데모로 전환하지 않습니다.
- 제공자 토큰·인가 코드·세션·비밀키는 URL, 분석 도구, 일반 로그에 기록하지 않습니다. 콜백 쿼리도 로그에서 제외합니다.

제공자 API를 이후 호출할 필요가 없다면 제공자 토큰의 영구 저장을 피합니다. 연결 해제 등 운영 목적에 보관해야 할 때만 암호화하고 최소 권한과 삭제 정책을 적용합니다.

## 회원과 로그인 계정

| 예정 테이블               | 핵심 필드·제약                                                             |
| ------------------------- | -------------------------------------------------------------------------- |
| `members`                 | 내부 UUID, 상태, 온보딩·생성·탈퇴 시각                                     |
| `auth_identities`         | 회원 FK, provider, provider subject, 연결 시각; `(provider, subject)` 유일 |
| `auth_sessions`           | 회원 FK, 세션 해시 유일, 유휴·절대 만료, 폐기 시각                         |
| `auth_login_transactions` | 일회성 state·바인딩·PKCE/nonce 정보, 목적, 만료·사용 시각                  |
| `legacy_auth_links`       | 기존 Supabase subject와 새 회원 ID의 유일 매핑, 이전 근거·시각             |

식별 키는 이메일이 아닌 검증된 제공자 subject입니다. 동시에 최초 로그인해도 동일 계정이 두 번 생성되지 않도록 유일 제약과 트랜잭션을 사용합니다.

다른 소셜 계정 연결에는 기존 서비스 세션의 재인증과 새 제공자의 인증이 모두 필요합니다. 이미 다른 회원에 연결된 계정은 자동 이동시키지 않습니다. 마지막 로그인 수단을 해제해 회원이 복구 불가능해지는 것을 막습니다. 이메일 일치만으로 회원을 병합하지 않습니다.

## 예정 HTTP 계약

모든 경로는 `/api/v1` 기준이며 아직 구현되지 않았습니다. 콜백은 제공자 인증 결과로 검증하고, 서비스 변경 API는 세션과 CSRF를 검증합니다.

| 메서드·경로                             | 역할                                                  |
| --------------------------------------- | ----------------------------------------------------- |
| `GET /auth/{provider}/start`            | `naver`, `kakao`만 허용, 로그인 트랜잭션 생성 후 이동 |
| `GET /auth/{provider}/callback`         | 코드 교환과 일회성 트랜잭션 검증, 서비스 세션 생성    |
| `GET /auth/session`                     | 최소 회원 정보·온보딩 상태 조회, 미인증은 401         |
| `POST /auth/logout`                     | 현재 세션 폐기                                        |
| `POST /auth/logout-all`                 | 재인증 후 모든 세션 폐기                              |
| `POST /auth/identities/{provider}/link` | 재인증 후 계정 연결 전용 트랜잭션 시작                |
| `DELETE /auth/identities/{provider}`    | 재인증 후 연결 해제, 마지막 수단 해제 차단            |

인증 실패는 401, 권한 부족은 403을 기본으로 하되 타 업체 자원의 존재를 숨겨야 하는 경우 404로 통일합니다. 오류는 `code`, 사용자용 `message`, `requestId`를 포함하고 토큰·제공자 원문 응답은 노출하지 않습니다. 제공자 장애는 재시도 안내와 함께 503 등으로 구분합니다.

## Expo WebView 복귀

외부 브라우저와 WebView의 쿠키 저장소가 공유된다고 가정하지 않습니다. 외부 인증 세션에서 로그인을 진행하고 앱 복귀를 별도 검증합니다.

기본안은 앱이 만든 challenge와 연결된 로그인 트랜잭션을 사용하고, 콜백 후 앱으로 짧은 수명의 일회성 전달 코드를 반환하는 것입니다. 앱은 verifier로 코드를 교환합니다. Go는 인증된 앱 흐름에서 WebView 바인딩을 포함한 일회성 부트스트랩 교환을 제공하고, WebView의 같은 출처 응답에서 HttpOnly 세션 쿠키를 설정합니다. 두 교환의 바인딩·원자적 소비·만료를 구현 전에 상세화하고 실기기로 검증합니다.

장기 세션이나 제공자 토큰을 딥링크 쿼리에 넣지 않습니다. 허용한 앱 링크와 복귀 경로만 사용하며 앱의 기존 동일 출처 탐색 정책에 필요한 변경을 명시합니다. 이 흐름이 검증되기 전에는 모바일 인증 전환 완료로 표시하지 않습니다.

## 설정과 운영 준비

아래 항목은 서버 전용 설정의 예정 목록입니다. 아직 `.env.example`이나 배포 설정에 추가하지 않습니다.

- 네이버·카카오 client ID, client secret, 환경별 등록 callback URL
- 공개 웹 기준 URL, 허용 복귀 경로·앱 링크, 프록시 신뢰 범위
- DB 연결, 쿠키 정책, 세션·로그인 트랜잭션 만료 정책
- 필요한 제공자 토큰 암호화 키와 회전 방법

개발·스테이징·운영 등록 정보를 분리합니다. 외부 공개 전에 제공자 앱 설정·필수 동의 항목·검수 요구를 확인합니다. 로그인 시작·콜백·교환 경로에 요청 제한을 두고 민감정보 없는 감사 이벤트를 기록합니다.

## 완료 조건

- 두 제공자의 신규·기존 회원 로그인, 동의 거부, 제공자 장애를 검증합니다.
- 위조·누락·만료·재사용 state, 코드 재사용, 허용되지 않은 복귀 URL을 거부합니다.
- 동시 최초 로그인, 계정 연결 충돌, 이메일 미제공에서도 회원을 정확히 구분합니다.
- 세션 회전·만료·로그아웃·전체 폐기·제재와 CSRF 차단을 검증합니다.
- SSR과 iOS·Android 실제 로그인 복귀, WebView 재시작·취소 흐름을 검증합니다.
- 기존 회원의 소유권과 이미지·채팅·찜 접근을 이전 전후 대조합니다.
