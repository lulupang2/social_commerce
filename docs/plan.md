# 개발 로드맵

기준일: 2026-09-18 · 신규 전환 작업은 구현 전입니다.

[제품 기준](SSOT.md) · [백엔드 전환 설계](backend-transition.md) · [인증 설계](authentication.md) · [입점사와 거래 설계](commerce.md)

배포·서버 테스트는 [nhn-rocky](deployment.md), DB는 Supabase PostgreSQL 유지, 큐는 River, PG는 토스페이먼츠 테스트 환경으로 확정했습니다. 서버 접속·Docker·Compose 확인만 완료했으며 실제 서비스 배포와 테스트 환경 구성은 아직 수행하지 않았습니다.

## 0. 방향과 설계

- [x] Go + Fiber 백엔드, 네이버·카카오 자체 인증 방향 기록
- [x] 기존 구조와 목표 구조, 인증·입점사·거래 설계 초안 작성
- [x] nhn-rocky SSH·Docker·Compose 읽기 전용 확인, 최종 DB는 Supabase 유지로 변경
- [x] BullMQ 도입 가능 여부와 River 대안 비교 문서 작성
- [x] River 채택, 토스페이먼츠 테스트 PG 선정
- [ ] River 연결·migration·권한, 격리 환경의 트랜잭션·재시도·자원 사용 검증
- [ ] 운영 데이터·회원 존재 여부, 기존 인증 의존성 목록 확정
- [ ] 세션 만료·복구 정책, 배포·도메인, 채팅 인증 경로 확정
- [ ] PG 지원 범위·계약, 수수료·배송·환불·정산 정책 확정

완료 조건: 미확정 정책을 결정 기록으로 남기고 운영 데이터의 이전·복구 범위를 확인합니다. 문서 작성 체크는 구현 완료를 의미하지 않습니다.

## 1. Go API와 원격 환경 기반

- [ ] nhn-rocky 원격 저장소·도메인·포트·자원 확인, 테스트·운영 Compose 분리
- [ ] Supabase 테스트 프로젝트 연결, 앱·River migration 적용과 기존 데이터·권한 보존 검증
- [ ] `apps/api` 구성, Go·Fiber 버전 고정, 설정·로그·오류·헬스 체크
- [ ] DB 런타임·마이그레이션 권한 분리, 회원 컨텍스트와 RLS 설계
- [ ] OpenAPI 계약과 TypeScript 클라이언트 생성 경로
- [ ] 동일 출처 프록시·요청 제한·배포·CI 검사

완료 조건: 기동·DB 연결·정상 종료와 미인증 접근 차단을 검증하고, 연결 풀에서 회원 컨텍스트가 다른 요청으로 누출되지 않습니다.

## 2. 인증 구현과 기존 회원 연결

- [ ] 내부 회원·외부 로그인 계정·세션·기존 회원 매핑 추가
- [ ] 네이버·카카오 콜백, 서비스 세션, 로그아웃·전체 폐기
- [ ] CSRF·재사용·리다이렉트 검증, 계정 연결·복구·제재
- [ ] Next.js SSR, Expo 외부 로그인·WebView 복귀

완료 조건: 두 제공자와 실제 모바일 복귀의 정상·실패 흐름, 계정 연결 충돌을 검증합니다. 이 단계만으로 기존 인증을 운영에서 종료하지 않습니다.

## 3. 기존 기능 이전과 인증 운영 전환

- [ ] 상품 등록·수정·조회 한 흐름을 Go로 이전
- [ ] 프로필·찜·커뮤니티·푸시 토큰·이미지·Edge Functions 이전
- [ ] 채팅·Realtime의 새 인증 경로 구현과 참여자 검증
- [ ] 기존 DB/API/RPC 직접 쓰기 차단, FK·RLS·삭제 전파 이전
- [ ] 데이터 대조·복구 연습 후 재로그인 전환과 Supabase Auth 종료

완료 조건: 새 회원과 이전 회원의 기존 기능이 모두 동작하고, 기존 직접 경로로 권한을 우회할 수 없습니다. 신규 기록을 보존하는 복구 절차를 검증합니다.

## 4. 입점사와 상품·재고

- [ ] 판매 주체·구성원·입점 신청·승인·정지
- [ ] 기존 개인 판매자 연결과 업체별 역할 검사
- [ ] 상품·재고, 입점사·운영자 화면

완료 조건: 승인된 업체만 판매하고 타 업체의 자원에 접근할 수 없습니다. 개인 중고거래 기능도 유지됩니다.

## 5. 주문·결제·환불

- [ ] 한 판매자 주문, 가격 스냅샷·재고 예약·만료
- [ ] 토스페이먼츠 테스트 승인·조회·취소·웹훅, 멱등성·River 결과 대조
- [ ] 배송·구매확정·부분 환불, 실패 상태 표시

완료 조건: 승인된 업체의 상품을 테스트 결제하고 해당 업체만 주문을 처리합니다. 동시 재고 경쟁·중복 승인·웹훅·PG 성공 후 DB 실패를 복구할 수 있습니다. 실제 결제 개시는 계약·운영 준비를 별도 확인합니다.

## 6. 정산과 지급

- [ ] 불변 원장·업체별 정산·지급 보류와 운영 조회
- [ ] worker 재시도·PG 대조·중복 지급 방지
- [ ] 지급 후 환불 조정, 장애 대응·감사 기록

완료 조건: 원장·주문·PG 금액을 대조하고 지급 실패·중복 요청·지급 후 환불을 검증합니다. 실제 지급은 계약과 셀러 검증이 완료된 뒤 활성화합니다.

## 검증 기록 방식

단계마다 실행 명령·환경·결과·날짜를 기록합니다. 서비스 테스트는 `nhn-rocky`의 격리 환경에서 수행하고 부하가 큰 빌드·통합 테스트는 순차 실행합니다. 문서 포맷 확인은 서비스 테스트와 구분합니다. Go 테스트·빌드, 웹·모바일 검사, DB 권한·동시성 검사, 외부 테스트 환경 확인을 변경 범위에 맞게 수행합니다. 아직 없는 Go 명령이나 PG 연동을 현재 실행 가능한 것으로 안내하지 않습니다.

## 이전 MVP 작업 기록

아래 체크와 테스트 수치는 기존 문서에서 보존한 이력입니다. 현재 커밋이나 신규 Go 구조에 대한 재검증 결과가 아닙니다.
